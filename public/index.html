                By default the broker never auto-approves writes, edits, network access, secrets or git writes; only with the opt-in workspace_edits scope may the advisor approve single-file edits inside the workspace during implement delegations (never secrets, CI, git metadata, lockfiles or agent-control files; own daily limit, audited). Advisory requests (advise_all) send by default only a minimal payload (request id, controlled action name, local risk, categories — no command, no resource names). Authority requests (low_only / advisor_assessed / workspace_edits) always send the documented redacted tuple; the toggle does not affect them. Redaction is best-effort, not a guarantee; the provider may retain what it receives.

                            Cretli in WSL2, Chrome on Windows
                            
            
                            In the default NAT network mode WSL cannot reach Windows localhost, and Chrome listens only on localhost, usually on IPv6 [::1]. Forward the port on the WSL virtual interface of Windows.
                            
            
                              
              
                            1. 
                In WSL, find the Windows address (the default gateway):
                
                              ip route show default | awk '{print $3}'
                              
              
                              2. 
              
                            2. 
                In PowerShell as administrator, forward that address to Chrome on IPv6 and allow only the WSL subnet through the firewall (replace 172.20.0.1 with the address from step 1):
                
                              netsh interface portproxy add v4tov6 listenaddress=172.20.0.1 listenport=9222 connectaddress=::1 connectport=9222
New-NetFirewallRule -DisplayName "Cretli CDP from WSL" -Direction Inbound -Protocol TCP -LocalPort 9222 -RemoteAddress LocalSubnet -Action Allow
                              
              
                              3. 
              
                            3. 
                Check from WSL, then enter http://172.20.0.1:9222 (your address) above:
                
                              curl http://172.20.0.1:9222/json/version
                              
              
                              4. 
            
                            
            
                            Connection reset (curl error 56) means the forward targets 127.0.0.1 while Chrome listens on [::1]: check with "netstat -ano | findstr 9222" on Windows and use v4tov6 as above.
                            
            
                            Never use listenaddress=0.0.0.0: it exposes the debugging port, and with it your Chrome profile, to the whole local network. Remove such a rule with "netsh interface portproxy delete v4tov4 listenaddress=0.0.0.0 listenport=9222".
                            
            
                            The Windows address on the WSL interface can change after a Windows or WSL restart; then update the forward and the address above. Alternatively, networkingMode=mirrored in %UserProfile%\.wslconfig (then wsl --shutdown) makes http://127.0.0.1:9222 work directly, but it changes networking for all of WSL.
                            
            
                            Anyone who can reach the debugging port controls that Chrome profile, including its cookies.
