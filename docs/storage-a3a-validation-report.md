## Addendum: barrier-inclusive replay (derived, not re-measured)

The `startupReplay` rows above follow the frozen A1 method: the thread closes the store (the close checkpoints the WAL) and reopens it, so the TRUNCATE barrier costs almost nothing there (`A1 barrier` ~0.014 ms). A restart that finds a WAL pays the barrier's fsync and checkpoint (`E2E barrier`). Deriving the barrier-inclusive replay without thread creation from this run's end-to-end samples (median of worker-reported open + barrier + cold page, spawn and handler import excluded) against the same 2x JSON budget:

## Startup verdict and cause

The primary medium startup gate FAILS under both views (clean-close 30.6 ms vs 15.9 ms; WAL-present ~55 ms vs 15.9 ms). The budgets are frozen and unchanged. The end-to-end start of ~79 ms adds ~23 ms of thread creation and handler import. The open phase (~34 ms on medium) is the production open path, which runs (likely the dominant share, not attributed here) read-only `integrity_check` and `foreign_key_check` over the whole database on every start of an existing store; the barrier adds ~14-20 ms of fsync/checkpoint when a WAL is present. The frozen baseline measured a plain open without these checks, so it was not comparing the same work. Attribution of the check share inside open is not measured in this published run (UNVERIFIED); a separate per-cold-process profile on a different synthetic dataset is in `docs/storage-a3a-startup-profile.md` (checks ~25.6 ms unmapped / ~20.8 ms mapped of a ~27 / ~23 ms open; it does not close this attribution; gate still FAIL, NO-GO).

## Limitations

- One run on one machine/filesystem; PASS would not be production rollout approval and no production caller or data is migrated.
- Budgets are the frozen docs/storage-gates.md values and are not changed here.
- Group commit requests carry up to 64 append calls; worker request/queue timings are per dispatched group or read, append latency is per durable caller promise.
- JSON rewrites once per append call with stronger fsync durability than the active legacy adapter; the worker also persists receipts and dedupe; max history retention (2000 per chat) applies to both.
- The A1 startup gate follows the frozen method (existing thread, spawn excluded) but uses the production open path, so it also pays integrity_check, foreign_key_check and the unconditional TRUNCATE barrier that the frozen baseline (plain open, no checks) did not; end-to-end start adds thread spawn and handler import. Both are reported, neither lowers a budget.
- Startup samples run with a warm OS page cache on copies of db+wal; a cold-disk restart is not measured.
- The Stop/claim/intent probe is a proxy (history appends submitted with those storage priorities); the real callers are not migrated.
- FULL checkpoint p99 is taken from a small number of samples per workload (idle: worker idle between batches; contended: fired while a batch is in flight) on a side connection, not from the worker.
- File growth is the frozen A1 I/O gate; Linux write_bytes is a process-wide diagnostic and never replaces it. No power-loss simulation or concurrent backups.

## Reproduce

```bash
CRETLI_BENCH_OUT=/tmp/chat-bench-a1-complete.json \
CRETLI_BENCH_MD=docs/storage-a3a-validation-report.md \
node scripts/storage-chat-history-bench.mjs
```

Set `CRETLI_BENCH_SCALE=10` for a smoke run (never PASS) and `CRETLI_BENCH_WORKLOADS=small,mixed` to subset. Results depend on disk fsync speed; re-run on the same machine class before comparing.
